# GGSel-copy - магазин цифровых товаров

Витрина цифровых товаров для геймеров + бэкенд с гарантией **однократной выдачи
ключа под гонками**, восстановлением после сбоев и промокодами с лимитом.

Стек: **Node.js + Express + better-sqlite3** (файл БД `data/app.db`), фронт - чистый
HTML/CSS/JS без сборки.

- Построчный разбор бэкенда - [backend.md](backend.md)
- Построчный разбор фронтенда - [frontend.md](frontend.md)

---

## Запуск

Требуется Node.js >= 20.

```bash
npm install
npm run seed          
npm start             
```

Открыть:

| Страница | URL |
|---|---|
| Витрина | http://localhost:3000/ |
| Статус заказа | http://localhost:3000/order.html?id=<order_id> |
| Админка | http://localhost:3000/admin.html (токен по умолчанию `dev-admin-token`) |

Ручной сценарий покупки: на витрине нажать **Купить** на любой карточке -> в модалке **Создать заказ** -> **Оплатить - успех** -> откроется страница статуса,
которая сама поллит заказ до выдачи ключа.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|

| `PROVIDER_TIMEOUT_MS` | `2500` | таймаут ожидания поставщика |

```bash
  -H 'x-admin-token: dev-admin-token' -H 'content-type: application/json' \
  -d '{"errorRate":0.3,"timeoutRate":0.3}'
```

## Живая витрина в реальном времени (этап 2, задача 1)

Наличие и цена на складе меняются, и это сразу видно во всех открытых вкладках
без перезагрузки. Транспорт - **SSE** (`GET /api/stream`), рассылка из
внутрипроцессного хаба, у клиента `EventSource` с авто-переподключением.

**Как воспроизвести:**

1. `npm start`, открыть витрину `http://localhost:3000/` в **двух** вкладках.
2. В третьей вкладке открыть админку `http://localhost:3000/admin.html`,
   подключиться токеном `dev-admin-token`. В панели **Каталог / склад** поменять
   цену или остаток любого из первых пяти товаров, нажать **Применить**.
3. В обеих вкладках витрины цифра меняется сразу, без F5. Поставить остаток `0` -
   кнопка **Купить** у всех превращается в неактивную **Раскуплено**.
4. Купить товар в одной вкладке (Купить -> Создать заказ -> Оплатить - успех) -
   во второй вкладке остаток этого товара уменьшается сам (вычет на оплате).
5. **Подорожание в корзине:** нажать Купить, модалку не закрывать, в админке
   поднять цену этого товара. В модалке новая цена и плашка «Товар подорожал».
   После **Создать заказ** сумма фиксируется и дальнейшие правки цены на неё не
   влияют.
6. **После перезагрузки:** F5 на вкладке витрины - состояние сразу верное
   (полный `GET /api/catalog/products` на загрузке).
7. **После обрыва связи:** DevTools -> Network -> Offline на пару секунд. Слева
   снизу плашка становится красной «переподключение...». Вернуть Online - плашка
   зелёная, и всё, что изменилось за время обрыва, подтягивается: события из
   буфера повторов по `Last-Event-ID` + полный ре-синк каталога при реконнекте.

## Гонка за последней единицей (этап 2, задача 2)

Единица склада занимается атомарно **в момент создания заказа**
(`POST /api/orders` -> `UPDATE products SET stock = stock - 1 WHERE stock > 0`),
а не при оплате. Поэтому из двух покупателей последней единицы один получает
заказ, второй - `409 out_of_stock` ещё до оплаты, списания у него нет.
`orders.stock_held` помечает заказ, держащий единицу; неуспешная оплата
возвращает её в продажу, выдача - окончательно списывает.

**Скриптом:** `npm run race:last-unit` (при запущенном `npm start`) или в составе
`npm run race:all`.

**Руками:**

1. `npm start`, открыть админку, в панели **Каталог / склад** выставить остаток
   какого-нибудь товара `= 1`, **Применить**.
2. Открыть витрину в **двух** вкладках, в обеих нажать **Купить** на этом товаре
   и дойти до кнопки **Создать заказ**.
3. Нажать **Создать заказ** в обеих вкладках почти одновременно.
4. Одна вкладка уходит на экран оплаты. Вторая показывает «Не получилось»:
   товар только что раскупили, оплата не списана, список товаров в наличии и
   кнопка «Вернуться к каталогу». Карточка товара гаснет в обеих вкладках.

## Бронь с таймером (этап 2, задача 3)

При создании заказа единица склада бронируется на `RESERVATION_MINUTES` (дефолт
3 мин), в заказ пишется `reserved_until`. Фоновый сборщик
(`src/services/reservations.js`) раз в несколько секунд снимает просроченные
брони: заказ -> `expired`, единица возвращается в `products.stock` и уходит
событие в живую витрину. Оплата после истечения отклоняется (`409
reservation_expired`). Успел оплатить до нуля -> заказ идёт в выдачу, таймер
больше ни на что не влияет.

**Скриптом:** `npm run race:reservation` (при запущенном `npm start`) или в
составе `npm run race:all`.

**Руками:**

1. Запустить с коротким сроком: `RESERVATION_MINUTES=1 npm start`.
2. На витрине купить товар, дойти до экрана оплаты - там идёт обратный отсчёт
   `01:00 -> 00:00` (последние 30 c красным). Тот же отсчёт на
   `order.html?id=...`, если открыть заказ по ссылке.
3. **Не оплачивать.** На нуле экран оплаты сменяется на «Бронь истекла», а в
   другой вкладке витрины остаток этого товара возвращается (+1) без
   перезагрузки.
4. Повторить и **оплатить** до нуля - заказ уходит на страницу статуса и
   доводится до выдачи ключа, отсчёт исчезает.
5. Без ожидания минуты: `POST /debug/orders/<id>/expire-reservation` мгновенно
   снимает бронь конкретного заказа.

Пока бронь жива, тот же товар нельзя забронировать под второй заказ - `claimStock`
(`UPDATE products SET stock = stock - 1 WHERE stock > 0`) уже увёл единицу в 0.

## Устойчивость покупки (этап 2, задача 4)

Покупку нельзя сломать двойным кликом, кнопкой Назад после оплаты, обновлением
страницы или обрывом связи.

- **двойной клик «Создать заказ»** — `orders.idempotency_key UNIQUE` + повторное
  использование: один заказ;
- **двойной клик «Оплатить»** — кнопки блокируются сразу; `event_id` стабильный
  (`evt_<orderId>_<paid|failed>`), повтор отсекается на `ON CONFLICT(event_id)`;
  переход `created -> paid` условный - вторая оплата ничего не делает;
- **Назад / обновление / обрыв** - id незавершённого заказа лежит в
  `localStorage` (`ggsel_pending`). На витрине сверху появляется плашка
  «Незавершённый заказ … - Продолжить оплату». «Купить» по тому же товару **не
  создаёт второй заказ**, а возобновляет существующую бронь (с тем же отсчётом).
  `order.html` по прямой ссылке всегда показывает верный статус;
- **повторная оплата уже оплаченного** - `POST /api/pay` на заказ в
  `paid`/`delivering`/`delivered` отвечает `{ noop: true }` и вебхук не шлёт.

**Скриптом:** `npm run race:resilience` (при запущенном `npm start`) или в
составе `npm run race:all`.

**Руками:**

1. Купить товар, дойти до экрана оплаты, **обновить страницу** (F5). На витрине
   сверху - плашка «Незавершённый заказ». Нажать «Продолжить оплату» - открывается
   тот же заказ с тем же отсчётом брони.
2. Оплатить. Открыть `order.html?id=...`, нажать **Назад**, снова открыть - статус
   верный, второй оплаты нет.
3. Несколько раз быстро кликнуть «Оплатить» - заказ выдаётся один раз, ключ один.

## Мгновенный поиск по большому каталогу (этап 2, задача 5)

Каталог раздут до `CATALOG_SIZE` (дефолт 3000) синтетических товаров
(`src/seed-data/generate.js`, детерминированный генератор). Витрина показывает
только «витринные» 12 (`products.featured = 1`), остальное доступно через поиск.

- **сервер:** `GET /api/search?q&type&min&max&sort&page&page_size` - `LIKE` по
  названию + фильтры + сортировка (`relevance`/`price_asc`/`price_desc`/`name`) +
  пагинация. По ~3000 строк отвечает за ~1 мс;
- **клиент** (`search.html`): ввод с debounce 150 мс, устаревшие ответы
  отбрасываются по счётчику запросов + `AbortController` (свежий ответ не
  перетирается старым), список не мигает (не очищается на время загрузки,
  обновляется одним `replaceChildren`), все фильтры в `?query` через
  `history.replaceState` - прямая ссылка открывает те же результаты.

**Скриптом:** `npm run race:search` или в составе `npm run race:all`.

**Руками:**

1. Открыть `http://localhost:3000/search.html` (или ввести запрос в шапке
   витрины и нажать Enter).
2. Печатать в поле запроса - список обновляется по мере ввода, без задержек и
   мигания.
3. Выставить тип, диапазон цены, сортировку - адрес страницы меняется. Скопировать
   URL в новую вкладку - открываются те же результаты и фильтры.
4. Медленная сеть (DevTools throttling) + быстрый набор - список всегда
   соответствует последнему запросу, промежуточные ответы не «моргают».

## Как воспроизвести проверку гонок

`npm run race:all` поднимает изолированный сервер на своём порту и БД и прогоняет
все сценарии подряд:

```bash
npm run race:all
```

Отдельные сценарии (нужен запущенный `npm start` в другом окне):

| Команда | Сценарий | Критерий приёмки |
|---|---|---|
| `npm run race:webhooks` | 50 параллельных вебхуков «paid» с **одним** `event_id` по одному заказу | 1 |
| `npm run race:webhooks-distinct` | 50 параллельных вебхуков с **разными** `event_id` по одному заказу | 1 |
| `npm run race:out-of-order` | вебхук приходит раньше заказа + запоздалый `failed` не по порядку | 3 |
| `npm run race:double-click` | два одновременных «Купить» с одним `idempotency_key` | этап 2 |
| `npm run race:empty-pool` | пустой пул -> `out_of_stock` без падения -> пополнение -> идемпотентный повтор выдачи | 4 |
| `npm run race:promo` | `LIMIT3` (30 параллельных) и `ONCEONLY` (25 параллельных) | 5 |
| `npm run race:provider-faults` | таймаут поставщика A (повтор с тем же `request_id`), fallback на B, оба недоступны -> восстановление | этап 3 |
| `npm run race:last-unit` | 8 одновременных заказов на последнюю единицу; неуспешная оплата возвращает резерв | этап 2, задача 2 |
| `npm run race:reservation` | бронь истекает -> товар возвращается всем; оплата до нуля уходит в выдачу; повторное истечение выданного заказа ни на что не влияет | этап 2, задача 3 |
| `npm run race:resilience` | двойной клик «Создать заказ» и «Оплатить», повтор оплаты выданного (noop), оплата проваленного заказа (409) | этап 2, задача 4 |
| `npm run race:search` | фильтры по типу/цене, сортировка, пагинация без пересечений, детерминизм, устаревший ответ приходит позже свежего | этап 2, задача 5 |

Каждый скрипт печатает `✓` / `✗` по проверкам и завершает процесс с ненулевым
кодом при провале. Проверяемые инварианты берутся из `GET /debug/stats`
(состояние пула, число записей выдачи, число выдач поставщика, применения промокодов).

Пример вывода `race:webhooks`:

```
  ответов 200: 50/50, из них "duplicate": 49
  статус заказа: delivered, ключ: LFXC-TNCS-BPCD
  пул claimed: 0 -> 1
  записей выдачи: 0 -> 1
  ✓ израсходован ровно один ключ
```

## Как обеспечена однократная выдача (коротко)

1. **Вебхук идемпотентен по `event_id`**: `INSERT INTO payment_events ... ON CONFLICT(event_id) DO NOTHING`.
   Повтор и параллельные доставки одного события отсекаются на входе (`changes === 0` -> `200`, ничего не делаем).
2. **Переход `paid -> delivering`** - условный `UPDATE orders SET status='delivering' WHERE status IN ('paid', ...)`.
   Из 50 параллельных обработчиков дальше проходит ровно один, остальные видят `changes === 0` и выходят.
3. **`request_id = req_<order_id>`** стабилен на все повторы. Поставщик идемпотентен по нему
   (`provider_issues.request_id` - первичный ключ): повтор после таймаута возвращает **тот же** ключ, а не новый.
   Значит таймаут != отказ.
4. **`deliveries.order_id`** - первичный ключ; `INSERT ... ON CONFLICT(order_id) DO NOTHING` - финальный
   предохранитель: один факт выдачи, один израсходованный ключ, даже если что-то пошло не так на шагах выше.
5. **Занятие ключа из пула** атомарно: `UPDATE key_pool SET status='claimed' WHERE id=(SELECT id FROM key_pool WHERE status='free' ORDER BY id LIMIT 1) RETURNING code`.
6. **Промокод**: `INSERT INTO promo_redemptions ... SELECT ... WHERE (SELECT COUNT(*) ...) < max_uses` -
   проверка лимита и вставка в одном запросе, лимит не превышается под параллелью. Скидку считает сервер.
7. **Восстановление**: `out_of_stock` / `delivery_failed` не роняют процесс. Фоновый досбор (каждые 8 с)
   и админский `POST /admin/orders/:id/retry` доводят заказ через тот же `request_id` - идемпотентно.

## Модель статусов заказа

```
основной путь:  created -> paid -> delivering -> delivered
оплата не прошла: created -> payment_failed  (финал)

пул пуст:        delivering -> out_of_stock -> (пополнение + retry) -> delivered
поставщики упали: delivering -> delivery_failed -> (retry) -> delivered
```

`out_of_stock` и `delivery_failed` - **восстановимые**, не ошибка. Идемпотентность:
повтор оплаты или повтор выдачи не меняет уже финальный заказ.

## HTTP API

**Витрина/заказы**
- `GET  /api/catalog/products` - каталог
- `POST /api/orders` - `{ sku, promo_code?, idempotency_key?, order_id? }` -> создать заказ (скидку считает сервер)
- `POST /api/orders/preview-promo` - `{ sku, code }` -> предполагаемая скидка и остаток лимита
- `GET  /api/orders/:id` - статус заказа + выданный ключ
- `POST /api/pay/:orderId` - `{ result: "success" | "failed", event_id? }` - эмуляция оплаты: шлёт вебхук по контракту

**Вебхук оплаты**
- `POST /webhook/payment` - `{ event_id, order_id, status, amount, currency, created_at }` -> всегда быстрый `200`

**Заглушки-поставщики**
- `POST /provider-a/issue`, `POST /provider-b/issue` - `{ request_id, sku, order_id }` -> `{ status:"ok", code }` | `409 out_of_stock` | `503`
- `POST /provider-a/config`, `POST /provider-b/config` - `{ errorRate?, timeoutRate? }` (под токеном)

**Админка** (заголовок `x-admin-token`)
- `GET  /admin/orders/unfulfilled` - «оплачен, но не выдан» + состояние пула
- `POST /admin/orders/:id/retry` - безопасная идемпотентная повторная выдача
- `GET  /admin/pool`, `POST /admin/pool/refill` (`{ codes? , count? }`), `POST /admin/pool/drain`

**Debug** (при `ENABLE_DEBUG`)
- `GET  /debug/health`, `GET /debug/stats`, `POST /debug/reset`

## Структура

```
src/
  schema.sql          таблицы (где стоят UNIQUE/PK - там и гарантии)
  db.js               подключение к SQLite, миграция при импорте
  config.js           настройки из env
  seed-core.js/seed.js заливка справочных данных из "Материалов"
  services/
    orders.js         создание заказа, расчёт скидки, идемпотентность по ключу
    promo.js          скидка на сервере + применение промокода в пределах лимита
    reconcile.js      продвижение статуса заказа по событиям оплаты
    fulfillment.js    ядро выдачи: delivering-слот, A -> B, deliveries, восстановление, досбор
    providerClient.js HTTP-клиент к поставщику (таймаут / out_of_stock / ошибка)
  routes/
    catalog.js orders.js pay.js webhook.js providers.js admin.js debug.js
  server.js           сборка приложения
public/               витрина, order.html, admin.html
scripts/              воспроизведение состязательных сценариев
```
